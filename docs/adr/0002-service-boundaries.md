# ADR-0002: Границы сервисов

- **Статус:** Accepted
- **Дата:** 2026-11-05
- **Решающие:** владелец проекта, AI-лид
- **Связанные документы:** `MASTER_PROMPT.md` A6–A7, A14; `docs/architecture.md`

## Контекст

Plant Market начинается как небольшой магазин, но Конституция требует микросервисной архитектуры с первого дня: своя БД у каждого сервиса, API Gateway как единственная внешняя точка входа, синхронные вызовы только там, где нужен немедленный ответ.

Одновременно проект ограничен 8 ГБ RAM (Colima 4 ГБ), поэтому количество сервисов и инфраструктуры должно быть минимальным. Kafka, Redis, gRPC и GraphQL в Phase 0 не добавляются.

## Решение

MVP состоит ровно из пяти сервисов:

| Сервис            | Порт | БД            | Ответственность                                                                 | Фаза |
| ----------------- | ---: | ------------- | ------------------------------------------------------------------------------- | ---- |
| `api-gateway`     | 8080 | —             | Маршрутизация, CORS, rate limit, `X-Request-Id`, проверка JWT                   | 0    |
| `auth-service`    | 8090 | `pm_auth`     | Пользователи, роли, refresh-токены, OIDC                                        | 0    |
| `catalog-service` | 8081 | `pm_catalog`  | Категории, продукты, варианты; позже — индивидуальные растения, партии, резервы | 0    |
| `order-service`   | 8083 | `pm_orders`   | Заказы, корзина, checkout-сага, статусы                                         | 2    |
| `payment-service` | 8084 | `pm_payments` | Платежи, webhooks, возвраты                                                     | 2    |

Правила:

1. У каждого сервиса своя БД. Общих таблиц и SQL-запросов к чужой БД нет (AR-1).
2. Внешний трафик идёт только через `api-gateway` (AR-2).
3. Синхронные REST/gRPC-вызовы — только для немедленного ответа: резерв остатка, расчёт цены и доставки (AR-3).
4. Остальное — асинхронно через outbox и события (AR-4). В Phase 0 — Spring events + outbox.
5. Checkout — сага с оркестратором в `order-service` (AR-5).
6. GraphQL — только в BFF для storefront/admin, не внутри сервисов (AR-6).
7. `tenant_id` — во всех бизнес-таблицах с первого дня (AR-7).
8. Никаких распределённых транзакций, 2PC, XA (AR-8).

### Когда добавлять новый сервис

Только по измеримому триггеру A14, никогда «на будущее»:

| Триггер                                            | Действие                        |
| -------------------------------------------------- | ------------------------------- |
| Логика остатков > 1500 строк или > 20 заказов/день | выделить `inventory-service`    |
| Уведомления отправляются вручную                   | выделить `notification-service` |
| > 5000 SKU или поиск p95 > 500 мс                  | добавить Meilisearch            |
| > 10 RPS на каталог или нужен кэш корзины          | добавить Redis                  |
| ≥ 3 внешних продавца                               | включать мультитенантность      |
| Меньше 2 независимых потребителей событий          | Kafka не добавлять              |

## Альтернативы

- **Монолит / модульный монолит.** Проще для 8 ГБ и одного разработчика, но противоречит AR-1 и усложняет будущее выделение сервисов. Отклонено по Конституции.
- **Сразу 11 сервисов из A7.** Не влезает в память и создаёт оверинжиниринг. Отклонено: MVP = 5 сервисов.
- **Общая БД с схемами.** Нарушает AR-1 и изоляцию данных. Отклонено.

## Последствия

- Нужны контракты (`contracts/`) и дисциплина версионирования API/событий.
- Нужны интеграционные тесты с Testcontainers и ArchUnit-тест, запрещающий импорт пакетов другого сервиса.
- Появляется операционная сложность: health checks, логи с `traceId`, runbooks.
- Границы пересматриваются только через новый ADR и подтверждение владельца.

## Проверка

- ArchUnit: сервис не импортирует пакет другого сервиса.
- Интеграционный тест: repository каждого сервиса работает только со своей БД.
- `docker compose config` показывает отдельные БД и отсутствие общих томов между сервисами.
