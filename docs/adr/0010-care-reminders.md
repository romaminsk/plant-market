# ADR-0010: Care-напоминания после покупки

- **Статус:** Accepted
- **Дата:** 2026-11-06
- **Решающие:** AI-лид (автономный режим владельца)
- **Связанные документы:** `MASTER_PROMPT.md` A12 (care-инструкции), Phase 3; ADR-0008, ADR-0009

## Контекст

Phase 3 требует care-напоминания для покупателей. Отдельный `notification-service` и Kafka
включаются только по триггерам A14, поэтому напоминания размещаются в `order-service`, который уже
владеет заказом, e-mail покупателя и SMTP-интеграцией.

## Решение

- `care_reminders` в `pm_orders`: одна запись на позицию заказа, привязка к `order_id` и
  `order_item_id`, интервал 1–365 дней, `next_send_at`, `active`.
- Напоминания создаются только по запросу покупателя (`POST /api/v1/orders/{orderId}/care-reminders`)
  и только для оплаченного заказа (`PAID/FULFILLING/SHIPPED/DELIVERED/COMPLETED`). Повторный
  запрос по тому же заказу идемпотентно возвращает активные напоминания.
- `DELETE /api/v1/care-reminders/{id}` — opt-out; запись остаётся в истории с `active=false`.
- Планировщик раз в 60 секунд выбирает до 50 просроченных активных напоминаний, отправляет письмо
  и сдвигает `next_send_at` на интервал. При ошибке SMTP напоминание не сдвигается и будет
  повторено на следующем цикле.
- Логи содержат только название растения, без e-mail и других PII.

## Последствия

- Расписание фиксированное (интервал в днях), без учёта сезона, типа растения и часового пояса
  покупателя; для MVP это осознанное упрощение.
- Нет push/Telegram/WhatsApp — только e-mail.
- При нескольких экземплярах order-service планировщик может отправить дубль; до Phase 4
  допустимо, вместе с outbox-блокировкой.
- `order_item_id` уникален среди активных напоминаний, поэтому после opt-out можно подписаться снова.

## Проверка

- `OrderFlowIntegrationTest.careRemindersCanBeOptedInListedAndDisabled` — создание, список,
  отправка due-напоминания (мок JavaMailSender), opt-out, 409 для DRAFT.
- `OrderApiE2ETest.careReminderOptInAndOptOut` — полный API-сценарий через gateway.
