01Что это за проект #

Plant Market — интернет-магазин редких комнатных растений в Беларуси. Его главная идея — WYSIWYG (what you see is what you get): покупатель получает именно тот экземпляр, который сфотографирован, а не «похожее растение с полки».

Аналогия

Обычный магазин растений продаёт «товар»: на фото — условная монстера, а приедет другая монстера, похожая. Plant Market продаёт «этого конкретного монстра»: у него есть код, фотографии листьев, корней и даже дефектов, история карантина и гарантия 48 часов. Как объявление «продаю этот диван, вот царапина на подлокотнике», а не «диваны в наличии».

Почему микросервисы, а не один монолит

Плюсы

Что даёт разделение

  • У каждого сервиса своя база — нет неявных связей через общие таблицы.
  • Можно менять и деплоить каталог, не трогая оплату.
  • Понятные границы ответственности: за заказ отвечает order, за растение — catalog.
  • Падение оплаты не роняет витрину каталога.
  • Хорошая учебная модель реальной распределённой системы.
Минусы

Чем приходится платить

  • Нельзя сделать JOIN между заказом и растением — только HTTP-вызовы.
  • Появляются сетевые ошибки, таймауты и частичные сбои.
  • Нужны саги/компенсации: «зарезервировали, но оплата не прошла — надо откатить».
  • Пять JVM на 4 ГБ Colima — тесно.
  • Для маленького магазина это избыточно; модульный монолит был бы дешевле.
Ключевая мысль

Микросервисы выбраны не потому, что «так модно», а как осознанный учебный и фазовый выбор. В MASTER_PROMPT зафиксированы границы и не-цели; в ADR-0002 объяснено, почему именно пять сервисов. Для реального запуска с 20 заказами в день проще было бы начать с монолита.

Резервирование: как не продать одно растение дважды

Когда покупатель нажимает «Оплатить», заказ ещё не оплачен. Нельзя просто пометить растение проданным — вдруг оплата не пройдёт. Поэтому catalog-service делает резерв на 15 минут:

  1. Блокирует строку растения или варианта в базе (SELECT … FOR UPDATE).
  2. Проверяет, что растение AVAILABLE, а у варианта хватает остатков.
  3. Ставит растению статус RESERVED или увеличивает reserved_quantity.
  4. Создаёт запись reservations со статусом ACTIVE и временем истечения.
  5. Если оплата прошла — CONFIRMED; если отмена или истечение — RELEASED / EXPIRED.
Аналогия

Это как табличка «Забронировано до 18:30» на растении в магазине. Пока табличка висит, другой покупатель не может его купить. Если человек не вернулся — табличку снимают, растение снова доступно.

Когда что-то пошло не так: RFC 7807

Все ошибки API выглядят одинаково — это стандарт RFC 7807 Problem Details. Вместо «просто 400» клиент получает машиночитаемый объект:

 JSON · 409 Conflict 
{
  "type": "https://plant-market.by/problems/conflict",
  "title": "Conflict",
  "status": 409,
  "detail": "Not enough stock for variant PLANT-001: available 2",
  "instance": "/api/v1/reservations",
  "traceId": "01a1b627-a631-7e72-9e00-a621ccac5e1f"
}

Поле traceId — это тот же X-Request-Id, который прошёл через все сервисы. По нему можно найти запрос в логах. Ошибки валидации добавляют массив errors с полями и сообщениями.

Rate limit: почему 60, 10 и 300

Gateway считает запросы в фиксированном окне 60 секунд отдельно для каждого IP и группы маршрутов:

  • 60/мин — публичные запросы (каталог, карточки);
  • 10/мин — login и register, чтобы не перебирать пароли;
  • 300/мин — запросы с токеном.

При превышении возвращается 429 с заголовком Retry-After. Ограничитель in-memory: при нескольких экземплярах gateway каждый считает по-своему. Это осознанное упрощение Phase 1; Redis появится по триггеру A14.

Находка ревью

Исправлено: authenticated-bucket определяется по валидному principal, окно общее через Redis, auth-service закрыт за gateway и не публикует порт. Подробнее — P1-3.

5.1 API Gateway — охранник и диспетчер

Gateway — единственная публичная дверь в backend. Он не хранит данные и не считает бизнес-логику. Его работа: проверить токен, проверить роли, ограничить частоту, добавить заголовки и перенаправить запрос в нужный сервис.

Маршрут Куда Кто может

Access-токен — это JWT (JSON Web Token), подписанный HS256. Его можно прочитать без секрета, но нельзя изменить так, чтобы подпись осталась валидной. Внутри:

Пароли: Argon2id

Пароль не хранится в открытом виде. Используется Argon2id — современный алгоритм хеширования, который специально сделан медленным и требовательным к памяти, чтобы перебор паролей был дорогим. В базе лежит только password_hash.

Аналогия

Пароль — это фарш. Хеш — котлета. Из котлеты невозможно восстановить исходный фарш, но можно проверить, что новая котлета сделана из того же фарша. Argon2id делает «котлету» очень дорогой: злоумышленнику нужно много памяти и времени на каждый вариант.

Refresh-токены и ротация

Access-токен живёт 10 минут. Refresh-токен — 7 дней, хранится в базе в виде SHA-256 хеша и одноразовый: при обновлении старый отзывается, выдаётся новый. Если старый токен попробуют использовать повторно, сервис отзовёт все активные refresh-токены пользователя — это признак кражи.

OAuth2 PKCE для storefront

Storefront не хранит пароль. Он отправляет браузер на /oauth2/authorize с code_challenge, получает код и меняет его на токены с code_verifier. Это защищает от перехвата кода: без verifier обменять код нельзя.

P0/P1: где auth слаб
  • Refresh-токен возвращается в JSON и хранится в JS-доступном месте (админка — localStorage).
  • Дефолтный JWT-секрет зашит в конфиги и compose; нет fail-fast при старте с дефолтом.
  • Нет проверки iss/aud при декодировании.
  • SAS-авторизации в памяти: рестарт auth-service разлогинивает OAuth-сессии.
  • Заблокированный пользователь может обновлять refresh-токен (нет проверки статуса).

Как считается доступный остаток варианта

int available =
    batchRepository.availableQuantity(variant.getId(), StockBatchStatus.AVAILABLE)

availableQuantity — это сумма remaining_quantity по всем партиям варианта со статусом AVAILABLE. Из неё вычитается уже зарезервированное. Строка варианта блокируется findByIdForUpdate, чтобы два параллельных checkout не увидели один и тот же остаток.

Партии и FIFO

При подтверждении оплаты остатки списываются из партий в порядке поступления (receivedAt), то есть сначала продаём то, что пришло раньше. Это FIFO. Партия с истёкшим карантином не должна продаваться; при освобождении карантина оператор нажимает «Выпустить».

Находки по catalog
  • P0: нет аутентификации вообще — прямой доступ к :8081 меняет склад.
  • P0: lost-update: админские update грузят сущность без блокировки и без @Version, поэтому могут перезаписать reserved_quantity или статус SOLD.
  • P1: медиа отдаётся с http://localhost:8081/media, а CSP storefront запрещает этот источник — загруженные фото ломаются.
  • P2: архивирование продукта не меняет статусы вариантов — архивный товар можно купить.
  • P2: adjust партии не проверяет активные резервы и может увести остаток в минус.

 OrderService.java 
private void payOrder(OrderEntity order) {
  if (order.getStatus() != OrderStatus.PENDING_PAYMENT) {
    throw ApiException.conflict("Only PENDING_PAYMENT orders can be paid");
  }
  PaymentResult payment =
      paymentClient.createPayment(order.getId(), order.getTotalMinor(), order.getCurrency());
  if (!"CONFIRMED".equals(payment.status())) {
    throw ApiException.conflict("Payment is not confirmed: " + payment.status());
  }
  catalogClient.confirm(order.getId());
  order.markPaid();
  record(order, OrderStatus.PAID, "order.paid");
}

Если payment прошёл, а catalog.confirm упал (например, резерв истёк), транзакция заказа откатится, но платёж останется CONFIRMED. Повторный pay создаст второй платёж. Нет Idempotency-Key, нет возврата, нет саги. Это главный денежный риск. Подробнее — P0-2.

5.6 Уведомления и Outbox — блокнот «не забыть отправить»

Когда заказ становится PAID или CANCELLED, нужно отправить письмо. Если отправлять письмо прямо в транзакции, можно получить «письмо ушло, а заказ откатился». Поэтому используется transactional outbox:

  1. В той же транзакции, что меняет заказ, в таблицу outbox_events пишется событие.
  2. Отдельный планировщик раз в 5 секунд читает неотправленные события.
  3. Публикует Spring-событие, слушатель отправляет письмо.
  4. При ошибке увеличивает attempts, ставит nextAttemptAt с экспоненциальной задержкой.
  5. После 5 попыток помечает событие dead; админ может сделать redrive.
Аналогия

Outbox — это блокнот на кассе: «после того как заказ реально сохранён, отправь письмо». Кассир сначала записывает заказ в журнал, потом ставит галочку в блокноте. Если почта недоступна, галочка остаётся, и через минуту курьер попробует снова.

Находки по outbox
  • Событие публикуется до коммита транзакции: письмо может уйти, а заказ откатиться.
  • Нет FOR UPDATE SKIP LOCKED: два экземпляра order-service отправят дубли.
  • SMTP без таймаутов: зависший почтовый сервер держит поток.
  • Письма уходят только для PAID/CANCELLED; остальные статусы игнорируются.

Деньги: почему 12000, а не 120.00

Все суммы хранятся в минимальных единицах в колонках bigint. Для BYN минимальная единица — копейка. Поэтому:

В базе На экране Почему так
12000 120,00 Br 12 000 копеек = 120 рублей.
259900 2 599,00 Br 2 599 рублей 00 копеек.
500 5,00 Br Доставка по Минску.
Почему не float

0.1 + 0.2 в компьютере может дать 0.30000000000000004. В магазине это превращается в «копейка потерялась» или «итог не сходится». Целые копейки такой проблемы не имеют: 10 + 20 = 30 всегда.

UUIDv7: ID, которые не ломают индекс

Все первичные ключи — UUID версии 7. Это 128 бит: 48 бит времени в миллисекундах, версия, вариант и случайные биты. В отличие от UUIDv4, они времени-упорядочены: новые ID больше старых, поэтому B-tree индекс в PostgreSQL не «дырявится» так сильно.

 UuidV7.java 
public static UUID generate() {
  long timestamp = System.currentTimeMillis() & TIMESTAMP_MASK;
  long randomA = RANDOM.nextLong() & RANDOM_12_BITS_MASK;
  long randomB = RANDOM.nextLong() & RANDOM_62_BITS_MASK;

  long mostSignificantBits = (timestamp << 16) | VERSION_7 | randomA;
  long leastSignificantBits = VARIANT_10 | randomB;
  return new UUID(mostSignificantBits, leastSignificantBits);
}

Пример ID: 0199c3a0-7d2e-7c3a-9f4e-2b1a6c8d0e11. Первые символы содержат время, поэтому сортировка по ID примерно соответствует сортировке по дате создания.

Время: только UTC

Все временные метки — Instant в Java и timestamptz в PostgreSQL. Hibernate настроен на UTC. Это значит, что в базе и API время всегда в UTC с суффиксом Z, а часовой пояс пользователя — задача отображения.

Миграции: Flyway

Схема создаётся и меняется только SQL-миграциями в src/main/resources/db/migration. При старте сервиса Flyway проверяет, какие миграции уже применены, и накатывает недостающие. Откатов нет — только вперёд, новые миграции.

 V1__create_order_schema.sql 
CREATE TABLE orders (
    id              uuid         PRIMARY KEY,
    customer_id     uuid         NOT NULL,
    status          varchar(30)  NOT NULL,

    shipping_minor  bigint       NOT NULL DEFAULT 0 CHECK (shipping_minor >= 0),

Транзакции и блокировки

  • Пессимистичная блокировка SELECT … FOR UPDATE — используется в резервах, оплате и отмене. Она держит строку, пока транзакция не завершится.
  • Оптимистичная блокировка @Version — используется в заказах и платежах. При конфликте версий Hibernate бросает исключение, и транзакция откатывается.
  • Транзакция на сервис — нельзя одной транзакцией охватить order и catalog: это разные базы. Поэтому согласованность достигается сагой и компенсациями, а не ACID между сервисами.
Что такое сага

Сага — это последовательность локальных транзакций, где каждая следующая выполняется после успеха предыдущей, а при сбое выполняются компенсирующие действия. В идеале: reserve → pay → confirm; при сбое confirm — refund и release. В текущем коде компенсаций не хватает, поэтому это одна из главных находок ревью.

Индексы и пагинация

Списки отдают PageResponse с items, page, size, totalElements, totalPages. В базе есть индексы по orders(customer_id, created_at DESC), orders(status), outbox(published_at, created_at) и другие. Поиск по продуктам использует LIKE '%term%' — на больших объёмах понадобится trigram-индекс (pg_trgm), иначе будет full scan.

Где данных может не хватить
  • Списки заказов и претензий не пагинированы — при росте истории станут тяжёлыми.
  • Нет tenant_id, хотя конвенция его требует; это отложено до Phase 4.
  • reservations.target_id — полиморфная ссылка без FK: база не гарантирует, что цель существует.

Шаг 7. Подтверждение резерва

После успешной оплаты order-service вызывает catalog.confirm(orderId). Catalog:

  • находит активные резервы заказа;
  • проверяет, что они не истекли;
  • для варианта списывает количество из партий по FIFO и уменьшает reserved_quantity;
  • для отдельного растения переводит RESERVED → SOLD;
  • помечает резерв CONFIRMED.

Затем заказ становится PAID, в order_status_history появляется запись, а в outbox_events — событие order.paid.

08Безопасность #

Безопасность — это не одна кнопка, а набор слоёв: кто ты, что тебе можно, как защищён канал, как хранятся секреты, что будет при атаке. Разберём каждый слой и честно покажем дыры.

CSRF: зачем нужен, если есть JWT

CSRF — это когда злоумышленник заставляет твой браузер отправить запрос на сайт, где ты уже залогинен. С bearer-токеном в заголовке Authorization CSRF не страшен: чужой сайт не может прочитать токен и подставить заголовок. Но storefront использует cookies, а cookies браузер отправляет автоматически. Поэтому BFF требует двойной токен:

  • сервер ставит cookie pm.csrf, доступную JavaScript;
  • клиент читает её и отправляет в заголовке X-CSRF-Token;
  • сервер сравнивает cookie и заголовок.

Чужой сайт может отправить cookie, но не может прочитать её значение и подставить заголовок.

Аналогия

Cookie — это пропуск, который охранник принимает автоматически. CSRF-токен — это кодовое слово, которое нужно произнести вместе с пропуском. Пропуск злоумышленник может подделать (браузер сам приложит), а кодовое слово — нет, потому что оно написано на пропуске, который чужой сайт прочитать не может.

XSS и CSP

React экранирует текст по умолчанию, поэтому «вставить HTML через имя растения» не получится. Единственное место с JSON-LD использует безопасную сериализацию. CSP дополнительно запрещает загружать скрипты и картинки с чужих доменов. Но:

  • admin CSP разрешает 'unsafe-inline' — это ослабляет защиту;
  • storefront CSP не разрешает http://localhost:8081, поэтому загруженные фото не видны;
  • admin хранит JWT в localStorage — при XSS токен утечёт.

Server Components vs Client Components

Next.js App Router по умолчанию рендерит компоненты на сервере. Это хорошо для каталога: HTML приходит уже с данными, SEO и первая отрисовка быстрые. Но корзина, фильтры и галерея требуют браузерных событий — это клиентские компоненты с 'use client'.

Server

Что рендерится на сервере

  • каталог, карточки, аккаунт, legal;
  • метаданные и JSON-LD;
  • запросы к gateway через fetch с cache: 'no-store'.
Client

Что живёт в браузере

  • корзина и счётчик в шапке;
  • фильтры каталога;
  • галерея и restock-форма;
  • checkout и cookie-баннер.

BFF: зачем прятать токены

BFF (Backend For Frontend) — это серверные роуты Next.js, которые браузер вызывает вместо прямых запросов к auth/order. Они хранят токены в httpOnly cookies, поэтому JavaScript их не видит. Схема входа:

  1. GET /api/auth/login?returnTo=/checkout генерирует PKCE verifier и state, кладёт их в httpOnly cookies, редиректит на /oauth2/authorize.
  2. Auth-service показывает форму входа и редиректит на /auth/callback?code=….
  3. Callback проверяет state, меняет код на токены через /oauth2/token.
  4. Токены кладутся в httpOnly cookies pm.access и pm.refresh; CSRF-токен — в читаемую pm.csrf.
  5. Checkout BFF добавляет Authorization из cookie и при 401 обновляет токен через refresh.
P0: open redirect

Проверка returnTo выглядит как «начинается с / и не начинается с //». Но строка /\evil.com проходит проверку, а new URL() превращает её в http://evil.com/. Это фишинг: пользователь логинится на настоящем сайте и попадает на чужой. Подробнее — P0-5.

Layout-аудит: как ловят «поехавшие» поля

Тест открывает страницу, собирает все видимые input/select/textarea/button, считает попарные пересечения прямоугольников и выход за viewport. Отдельно проверяет, что таблица либо помещается, либо её контейнер скроллится.

 LayoutAuditE2ETest.java · фрагмент 
const controls = [...document.querySelectorAll('input, select, textarea, button')]
  .filter(visible);
const rects = controls.map((el) => ({ el, rect: el.getBoundingClientRect() }));

for (let i = 0; i < rects.length; i++) {
  for (let j = i + 1; j < rects.length; j++) {
    const a = rects[i], b = rects[j];
    if (a.el.contains(b.el) || b.el.contains(a.el)) continue;
    const x = Math.max(0, Math.min(a.rect.right, b.rect.right) - Math.max(a.rect.left, b.rect.left));
    const y = Math.max(0, Math.min(a.rect.bottom, b.rect.bottom) - Math.max(a.rect.top, b.rect.top));
    if (x * y > 4) problems.push('overlap ' + describe(a.el) + ' / ' + describe(b.el));
  }
}

Мутационное тестирование: проверка самих тестов

Обычное покрытие говорит, что код исполнялся. Мутационное — что тесты замечают ошибку. PIT берёт класс, вносит дефект (меняет + на -, убирает проверку, подменяет возврат) и смотрит, упадёт ли тест. Если тест прошёл — мутант выжил, проверка слабая.

Почему JUnit 4 bridge

Основной suite — JUnit 6, а PIT-плагин 1.2.3 не исполняет JUnit 6. Поэтому для PIT добавлены маленькие JUnit 4 тесты *MutationTest. Они не входят в обычный прогон и нужны только мутационному анализу. Когда PIT поддержит JUnit 6, bridge можно удалить.

Что сделано действительно хорошо

Архитектура

Чёткие границы

Пять сервисов, у каждого своя база и ответственность. Нет общих таблиц и скрытых JOIN. Gateway — единая точка входа. Это лучше, чем «микросервисы» из одного репозитория с одной БД.

Домен

Инварианты и состояния

Явно описаны жизненные циклы растения, заказа, платежа, резерва и претензии. Деньги — целые, ID — UUIDv7, время — UTC. Это взрослые решения, а не «так получилось».

Деньги

Сервер считает итог

Клиент не может подставить цену. Snapshot цены в заказе защищает от изменения прайса. Резерв на 15 минут и пессимистичная блокировка не дают продать последнее растение дважды в счастливом пути.

Надёжность

Outbox и retry

Событие пишется в одной транзакции с заказом, ретраится с backoff, уходит в dead-letter и может быть перезапущено админом. Для демо это сильно выше среднего.

Тесты

Не только «клики»

350 сценариев, 100 UI-матрица, layout-аудит, Lighthouse, Testcontainers, PIT. Есть проверка не только «страница открылась», но и «цена сошлась», «поле не наложилось», «мутант убит».

Документация

Честность

Status, ADR, runbooks и review-документы прямо называют блокеры: legal, localStorage, отсутствие idempotency. Это редкость: обычно документация продаёт, а не признаёт.

UX

Цельный дизайн

Dark Premium, реальные фото, адаптив, понятные пустые состояния, аккуратные формы. Витрина не выглядит как студенческий шаблон.

CI

14Словарь «на пальцах» #

Если встретил незнакомое слово — ищи здесь. Формулировки намеренно бытовые, но технически не врут.

API

Набор «дверей», в которые можно постучать из другой программы. У каждой двери есть адрес (endpoint), метод (GET/POST) и формат ответа.

REST

Стиль API, где ресурсы — это существительные (/products, /orders), а действия — HTTP-методы. GET читает, POST создаёт, PUT меняет, DELETE удаляет.

JSON

Текстовый формат «ключ: значение», который понимают все языки. Выглядит как JavaScript-объект, но это просто текст.

Микросервис

Отдельная программа со своей зоной ответственности и своей базой. Общается с другими по сети. Противоположность монолиту.

Монолит

Одна большая программа, где всё в одном процессе и одной базе. Проще в разработке, сложнее масштабировать по частям.

Gateway

Единая входная дверь. Проверяет пропуск, ограничивает частоту и направляет в нужный сервис. Клиент не знает, где живёт каталог.

BFF

Backend For Frontend — серверный слой специально под конкретный фронтенд. Прячет токены, CSRF и склеивает несколько API в один удобный вызов.

JWT

Подписанный «паспорт» пользователя. Его можно прочитать, но нельзя изменить без секрета. Внутри — кто ты, какие роли и до какого времени действует.

Access / Refresh

Access — короткий пропуск (10 минут). Refresh — длинный (7 дней), чтобы получить новый access, не вводя пароль.

OAuth2 / PKCE

Способ входа через отдельный сервис без передачи пароля приложению. PKCE добавляет одноразовый секрет, чтобы перехваченный код нельзя было обменять на токен.

CSRF

Атака «чужой сайт заставляет твой браузер отправить запрос». Защита — одноразовый токен, который чужой сайт не может прочитать.

CORS

Правила браузера, каким сайтам можно ходить в API. Сервер явно перечисляет разрешённые origin'ы.

CSP

Content Security Policy — список того, откуда странице можно грузить скрипты, стили и картинки. Если источника нет в списке, браузер его заблокирует.

XSS

Внедрение чужого JavaScript в страницу. Может украсть токен, cookie или сделать запрос от твоего имени.

Транзакция

Набор изменений в базе, который применяется целиком или не применяется вовсе. Как перевод денег: списание и зачисление вместе.

ACID

Свойства транзакции: атомарность, согласованность, изоляция, долговечность. Проще: «всё или ничего, и не потеряется».

Пессимистичная блокировка

«Я первый, ждите». Строка блокируется на время транзакции. Дорого, но надёжно для остатков.

Оптимистичная блокировка

«Проверим версию при записи». Если кто-то успел изменить строку — будет ошибка и повтор. Дешевле, но требует обработки конфликтов.

N+1

Когда на список из 100 элементов делают 1 запрос за списком и ещё 100 за деталями. Медленно. Лечится join/fetch.

Индекс

Алфавитный указатель в книге. Без него база читает всю таблицу, с ним — сразу нужные строки. Замедляет запись, ускоряет чтение.

UUIDv7

128-битный ID, в котором зашито время. Новые ID больше старых, поэтому база вставляет их эффективнее, чем случайные UUIDv4.

UTC

Единое мировое время без часовых поясов. В базе и API — UTC, на экране — местное время пользователя.

Минимальные единицы

Деньги в копейках/центах целым числом. 12000 = 120,00 BYN. Никаких float.

WYSIWYG

What You See Is What You Get. Покупатель получает именно тот экземпляр, который на фото, а не «похожий».

SKU

Stock Keeping Unit — внутренний код товара. У варианта свой SKU, у растения — код экземпляра.

Вариант

Продаваемая конфигурация продукта: размер, горшок, форма. У варианта есть цена и остаток по партиям.

Экземпляр

Одно конкретное живое растение с кодом и фото. Продаётся один раз, количество всегда 1.

Партия

Коробка растений от поставщика: сколько пришло, почём, когда, до какого числа карантин.

Карантин

Временный запрет на продажу после привоза. Растение адаптируется, проверяют на болезни.

Резерв

Бронь на 15 минут. Растение ещё не продано, но другой покупатель его уже не купит.

Сага

Цепочка локальных транзакций в разных сервисах. Если шаг упал — выполняются компенсации (отменить резерв, вернуть деньги).

Компенсация

Обратное действие после сбоя: release резерва, refund платежа, отмена заказа.

Идемпотентность

Свойство «повтор не меняет результат». Два одинаковых запроса на оплату должны создать один платёж, а не два. Обычно через Idempotency-Key.

Outbox

Таблица-блокнот: событие пишется в той же транзакции, что и заказ, а отправляется отдельно. Так письмо не уйдёт, если заказ откатился.

Dead-letter

«Мёртвое» событие, которое не удалось обработать после нескольких попыток. Его разбирают вручную или перезапускают.

Rate limit

Ограничение частоты запросов. Защищает от перебора паролей и перегрузки.

Testcontainers

Библиотека, которая поднимает настоящий PostgreSQL в Docker на время теста. Тесты работают с реальной базой, а не с заглушкой.

Playwright

Инструмент, который управляет настоящим браузером: кликает, вводит текст, проверяет, что видит пользователь.

Мутационное тестирование

Проверка качества тестов: в код специально вносят дефект и смотрят, упадёт ли тест. Если нет — тест слабый.

PIT

Инструмент мутационного тестирования для Java. Меняет байткод и запускает тесты.

Allure

Генератор красивых отчётов о тестах: шаги, вложения, скриншоты, история.

Lighthouse

Инструмент Google, который оценивает производительность, доступность, SEO и best practices. В проекте — порог a11y 0.95.

SSR / гидратация

SSR — HTML рендерится на сервере. Гидратация — браузер «оживляет» его, подключая обработчики. До гидратации кнопки могут не работать.

localStorage

Хранилище в браузере, доступное JavaScript. Живёт долго, но не отправляется на сервер автоматически. Уязвимо к XSS.

httpOnly cookie

Cookie, которую JavaScript не может прочитать. Хорошее место для токенов, если настроены Secure/SameSite.

16FAQ #

Почему для маленького магазина выбраны микросервисы?

Это осознанный учебный и фазовый выбор, а не оптимальная архитектура для 20 заказов в день. Границы позволяют показать реальные распределённые проблемы: саги, outbox, независимые БД. Для продакшена с малой нагрузкой модульный монолит был бы дешевле в эксплуатации.

Почему у каждого сервиса своя база?

Чтобы сервисы не лазили в чужие таблицы и не появлялись неявные связи. Цена — нельзя сделать JOIN между заказом и продуктом; данные собираются HTTP-вызовами. Это дисциплина границ, но добавляет сетевые сбои и сложность.

Зачем два механизма аутентификации — свой API и OAuth2?

Свой API /api/v1/auth/* удобен для админки и тестов. OAuth2 PKCE нужен storefront, чтобы не хранить пароль и держать токены в httpOnly cookie. Две системы — источник дублирования и рассинхронизации; в идеале оставить одну.

Почему в админке токен в localStorage, если это небезопасно?

Это известный pre-prod блокер, зафиксированный в документации. Для демо проще; для прода нужен BFF с httpOnly cookie, коротким access и refresh rotation. Пока токен в localStorage, любая XSS крадёт его.

Почему нет Kafka и Redis?

По конституции проекта они вводятся только по триггерам A14: когда outbox-таблицы и in-memory лимитов перестаёт хватать. Сейчас используется Spring Events + outbox и ConcurrentHashMap для rate limit. Это дешевле и достаточно для демо.

Как хранятся деньги и почему нельзя float?

Все суммы — bigint в копейках. 12000 = 120,00 BYN. Float ошибается на дробях (0.1 + 0.2), а в деньгах это недопустимо. Форматирование в «120,00 Br» делает фронтенд.

Что будет, если два человека одновременно купят последнее растение?

В счастливом пути — один получит резерв, второй 409. Это обеспечивает SELECT … FOR UPDATE и проверка остатка. Но админский update без версии может сломать это правило (P0-6), поэтому гарантия пока не абсолютная.

Почему оплата всегда успешна?

Потому что провайдер — WireMock-заглушка. Она отвечает AUTHORIZED на любой запрос. Реальные деньги не двигаются. Для продакшена нужен настоящий провайдер, webhook с подписью, refund и reconciliation.

Почему 478 E2E — это не слишком много?

Для демо — много, но полезно: 350 сценариев покрывают комбинации, 100 матрица — страницы и адаптив, 2 layout — вёрстку, остальные — сквозные пути. Минус — время прогона (~8–10 минут) и риск флаки. В CI стоит разделить smoke/regression/nightly.

Почему мутация только для platform-common?

Сервисные тесты используют Spring и Testcontainers, PIT с ними работает медленно и требует Arcmutate Spring plugin. Начали с маленьких чистых классов, где результат легко интерпретировать: 20 мутантов, 20 убито. Следующий шаг — сервисные unit-тесты без инфраструктуры.

Что чинить первым, если завтра запускать?

P0: закрыть catalog/payment, убрать дефолтные секреты, ввести Idempotency-Key и компенсации, перевести админку на httpOnly cookie, починить open redirect и ключ галереи. Без этого реальные деньги и персональные данные пускать нельзя.

Как добавить новый товар?

Через админку: создать категорию (если нужно) → продукт → вариант → экземпляр растения (или партию для варианта) → загрузить фото. Для WYSIWYG нужен именно экземпляр с кодом и фото, а не только продукт.

Где хранятся фотографии?

В локальном Docker-volume media-data, отдаются через gateway по /media/**; MEDIA_PUBLIC_BASE_URL совпадает с разрешённым img-src. В проде нужен S3/MinIO (ADR-0011).

Что такое outbox и зачем он нужен?

Это таблица событий, которая пишется в одной транзакции с бизнес-изменением. Отправка письма/события происходит отдельно. Так нельзя получить «письмо ушло, а заказ не сохранился». Минус — at-least-once: возможны дубли, поэтому нужна идемпотентность получателя.

Как посмотреть письма, которые «отправил» магазин?

Открой MailHog. Все письма перехватываются там; наружу ничего не уходит.

Почему в каталоге 11 растений, а в тестах — 98?

E2E-сценарии создают данные через API и не удаляют их. После полного прогона база загрязняется. Перед чистым прогоном нужен demo-reset. В CI база одноразовая, поэтому там этой проблемы нет.

Это готовый проект для портфолио?

Да, как демонстрация навыков — очень сильный: архитектура, домен, тесты, CI, UI, docs. Но в резюме/презентации честно указывай границы: sandbox-платежи, demo-данные, известные pre-prod блокеры. Это вызывает больше доверия, чем «всё готово».
